### F01 [critical] Unresolvable claim permanently wedges `main` for its base; no abandon/re-freeze API, put_ref guard ignores lease
- Where: hf2l/exchange/api.py:457, hf2l/exchange/api.py:482, hf2l/exchange/api.py:492, hf2l/exchange/api.py:543, hf2l/exchange/api.py:126, hf2l/backends/exchange.py:88, hf2l/owner_fedavg.py:268, hf2l/owner_fedavg.py:295, hf2l/owner_fedavg.py:314, hf2l/owner_fedavg.py:384, hf2l/exchange/models.py:109, hf2l/exchange/models.py:122, docs/EXCHANGE_SERVICE.md:203, docs/EXCHANGE_SERVICE.md:205, docs/EXCHANGE_SERVICE_DESIGN.md:344
- Sources: security, concurrency, sdk, drift, opsdoc, architecture, seed
- Claim: Once POST /claims freezes inputs for a base, that base is unpublishable by anyone until the claim gets a result_id: put_ref's guard (api.py:457-459) ignores lease/holder/workflow, re-acquisition reuses the frozen inputs (api.py:483-490), claims:publish requires exact input equality (api.py:543-544), there is no delete/abandon route, ready records are immutable, and a new workflow name re-freezes the same records. Because owner_fedavg claim mode is non-automatic and raises on any manifest/allowlist/tensor validation failure, a single bad or malicious training.update (or the orphan claim from the F56 race) permanently blocks main for that base; the only API-level escapes are falsifying input_record_ids via the SDK or moving main through a base-less non-model.global record, both of which break provenance. Needs an authenticated abandon/terminal-state operation or lease-scoped guard, coordinator-supplied or re-freezable inputs, and skip-not-raise handling in claim mode.
- Failure scenario: Coordinator runs owner_fedavg --claim-submissions --publish; the frozen set [A,B] includes bob's update with wrong tensor dtype/shape or a mismatched manifest; validate_compatible raises, process exits 1. Subsequent --claim-submissions returns claim_busy until expiry then re-freezes [A,B] and fails identically; --submission A C --publish aggregates but set_ref main -> 409; claims:publish with subset -> claim_inputs_mismatch. main never leaves the base until someone edits exchange_claims, publishes a record that falsely declares input_record_ids=[A,B], or moves main to a base-less non-model.global record.
- Verifier reasoning: Every element reproduced against the real app (SQLite+Moto). api.py:457-459 rejects any PUT /refs/main whose target.base_id matches a claim with result_id NULL, with no lease/holder/workflow filter — PUT returned 409 active_claim_requires_fenced_publication both with an active lease and after I set lease_until=1, and for a second coordinator. api.py:483-490 re-acquisition after expiry returned the same claim ID with identical inputs and fence 2; api.py:543-544 rejected a subset result with 409 claim_inputs_mismatch; DELETE /claims/{id} and POST :abandon returned 405 (routes api.py:476-547 have no terminal-state operation); bob's own ready update was undeletable (api.py:347-348, 409 record_immutable); a fedavg-2 workflow claim re-froze the same two inputs (api.py:492-493 selects all ready updates, ClaimInput schemas.py:96-99 accepts no inputs list); and the only path that moved main was a lineage-breaking hop to a base-less 'configuration' record then a model.global based on it (guard misses NULL base_id, move_ref's base check at api.py:126 applies only to model.global). On the CLI side owner_fedavg.py:233 makes claim mode non-automatic, so any per-input failure at :288/:305/:337 or validate_compatible at :388 raises and exits 1 on every retry — one malformed contributor update (or the orphan claim from F56) wedges the base. EXCHANGE_SERVICE.md:203-206 discloses that inputs are retained and stale workers cannot bypass, but not that the coordinator itself has no sanctioned recovery; design §7 (EXCHANGE_SERVICE_DESIGN.md:345-349) frames freezing as a coordinator decision while the code lets the server pick with no override. Critical on the given scale: permanently stuck base with no API-level recovery short of DB surgery, falsified input_record_ids, or a provenance-breaking main move, and any single contributor can trigger it.
- Recommendation: Add an authenticated DELETE /claims/{id} or POST /claims/{id}:abandon (holder or admin, fence-checked) that sets a terminal state and releases the put_ref guard; scope the guard to claims with an active lease (or rely on ref generation CAS); allow POST /claims to accept a coordinator-supplied/explicit inputs subset or re-freeze after expiry; make owner_fedavg claim mode skip (not raise) on per-input validation failures and abandon the claim on fatal failure; document the policy in EXCHANGE_SERVICE.md.

### F02 [high] A participant with two ready updates for one base permanently breaks claim creation and automatic discovery; ready records cannot be withdrawn

- Claim: Nothing enforces one ready training.update per (space, participant, base). Ready records cannot be cancelled by the creator (record_immutable) or by the coordinator/admin (not_record_owner), and the withdrawal flag promised in the design does not exist. Not critical: because the 409 fires before session.add at api.py:502, no claim row exists, so a coordinator can still recover with explicit --submission IDs plus an unfenced PUT /refs/main (probe returned 200), and advancing main clears the condition for later rounds.
- Recommendation: Select the newest ready record per participant deterministically in both claim creation and owner discovery (reporting superseded IDs as skipped), or accept an explicit inputs list on POST /claims, or enforce one ready update per (space, participant, base) at publish; add the designed audited withdrawal flag; document duplicate_participant/claim_completed and the recovery in EXCHANGE_SERVICE.md and fix the error text.

### F06 [high] One contributor request can reserve the whole space quota for 24 h; no per-principal cap, no admin cancel, revocation does not release
- Where: hf2l/exchange/api.py:251, hf2l/exchange/api.py:250, hf2l/exchange/api.py:343, hf2l/exchange/api.py:52, hf2l/exchange/api.py:214, hf2l/exchange/schemas.py:185, hf2l/exchange/worker.py:16
- Sources: security
- Claim: Quota is enforced only per space with no per-principal or per-record cap below the 5 TiB-per-attachment schema limit, so one contributor request can reserve all remaining quota for upload_seconds (fixed at 86400 s; not settable through the environment). Drafts of other principals are invisible to admins and coordinators and can only be cancelled by their creator, revoking the creator does not release the reservation and prevents the creator from cancelling, and the worker reclaims it only after expiry. Any admitted contributor can therefore block all record creation in the space, including the coordinator's aggregate publication, for up to 24 hours with no administrative recovery, contrary to the design's per-space-and-principal quota; the ops guide's per-principal rate-limiting disclaimer does not cover this.
- Failure scenario: A contributor POSTs /records with one attachment whose size_bytes equals remaining quota and never uploads; all others get 429 space_quota_exceeded for 24 h; the admin has no API to cancel or reclaim; attacker repeats at expiry.
- Verifier reasoning: Reproduced offline on the default 1 TiB space: a single POST /records from contributor alice with one attachment sized to the remaining quota returned 201 (api.py:250-253 checks only space.allocated against space.quota; schemas.py:46 allows 5 TiB per attachment and RecordInput allows 256 of them), bob's 1-byte record then returned 429 space_quota_exceeded, and DELETE by the space creator (admin+coordinator+reader) and by an admin-only member both returned 404 record_not_found because visible() (api.py:52-57) hides another principal's drafts and cancel_record additionally requires owner=True (api.py:346); the owner cannot even GET the draft. Setting alice's roles to [] via put_member (api.py:214-227) left allocated at the full quota, and the revoked alice's own DELETE then returned 404 space_not_found (api.py:46-47), so the reservation is unreleasable until worker.py:16-24 expires it after expires_at. upload_seconds is fixed at 86400 in config.py:19 and Settings.from_env (config.py:34-46) does not read it, so the CLI cannot shorten the window. DESIGN.md:87-88 promises a quota per space and principal; EXCHANGE_SERVICE.md:237-239 only disclaims per-principal rate limiting, which would not stop a single full-quota reservation. Severity stays high: the attacker must be an admitted contributor and the state self-heals in 24 h, but the outage also blocks the coordinator's own aggregate publication (publish_aggregate creates a model.global record with attachments), admins have no API remediation, and abandoned drafts from ordinary client retries accumulate the same way.
- Recommendation: Add per-principal outstanding-reservation limits (bytes and draft count), an admin/coordinator route to cancel or expire another member's draft, release reservations when roles are emptied, and make upload_seconds configurable.

The design's admin row (DESIGN.md:117) promising quota/rule/retention changes is not implemented; the ops guide discloses the retention half but not quota immutability; tests/test_exchange.py:168 bypasses the gap via the ORM.

- Recommendation: Add admin PATCH /v1/spaces/{id} for quota_bytes and rules (validate schemas as in create, with If-Match and an event), and an administrative retention path (e.g. POST /records/{id}:retire for unreferenced ready records that releases quota and hands versions to worker cleanup with a live-ref check) or at least a transactional CLI admin command; test quota through the API; fix the design table or document creation-time-only in the ops guide.

### F09 [high] Worker is single-threaded and sequential with no per-blob claiming; extra workers duplicate reads, one large verify blocks all recovery, and the fixed 24 h draft TTL includes verification time
- Where: hf2l/exchange/worker.py:26, hf2l/exchange/worker.py:31, hf2l/exchange/worker.py:12, hf2l/exchange/worker.py:62, hf2l/exchange/worker.py:16, hf2l/exchange/storage.py:92, hf2l/exchange/api.py:258, hf2l/exchange/api.py:332, hf2l/exchange/cli.py:237, hf2l/exchange/client.py:103, docs/EXCHANGE_SERVICE.md:51, docs/EXCHANGE_SERVICE.md:221
- Sources: concurrency, operability, seed, architecture
- Claim: tick() verifies blobs one at a time in a single thread with no per-blob claiming (worker.py:13-15, 26-63), so additional worker processes re-hash the same in-progress blob (verified: two concurrent ticks both called storage.verify and both reported verified=1) and aggregate throughput is capped at one object stream; a single multi-hundred-GiB verify blocks all other recovery/cleanup in that tick. ### C07 [low] SDK treats the designed transient 409 upload_initialization_pending as fatal; a single S3 blip in create_multipart_upload fails the whole put_record until a worker tick passes

## Lens summaries

**security**: Repository root: /home/iscyang/wksp/repos/github/hf_fl. Through the security/trust-boundary lens the core controls are solid and were verified rather than assumed: RS256-only JWT validation with typ/iss/aud/exp/iat/sub/scope checks and a uniform 401; membership re-read under a Space row lock on every route; space-scoped lookups and same-space foreign keys on every record/blob/ref/claim ID (no IDOR found); presigned grants that sign key, uploadId, partNumber, content-length and versionId; a separate transfer client that never carries the bearer token; and worker cleanup confined to server-generated unique keys of expired/cancelled drafts. The real weaknesses are availability and invariant gaps exploitable by an ordinary contributor rather than authentication or confidentiality bypasses: one request can reserve the whole space quota for 24 h with no admin remedy, a single unusable submission wedges any acquired claim with no abandon route, and duplicate submissions block claim creation outright, while the main-ref lineage/claim guard can be sidestepped by a stale coordinator through a baseless target, contradicting the docs. Lower-severity items are identity-snapshot staleness at publish, an attachment shadowing the inline manifest, an incomplete remote-schema filter, unenforced HTTPS for the storage endpoint, and a tenant concept that exists only as a label. I would fix the two high findings (per-principal reservation limits plus admin cancel; claim abandon plus a correctly keyed guard) before building further on the claim workflow, and note that the whole-space FOR UPDATE on every request, including 256-item reads with N+1 blob queries, lets any member serialize the space and deserves attention from the concurrency lens.

**concurrency**: Through the concurrency/consistency/crash-recovery lens the core discipline is sound: every S3 call happens outside a database transaction, all quota moves and every worker write re-check state under the per-space FOR UPDATE lock, and lost responses at upload start/complete are reconciled from the service-owned key and pinned version, so the happy-path blob pipeline survives crashes at each boundary without duplicate visible records. The serious gaps are in what the state machines omit rather than in races: a claim can never be released or re-frozen, a ready record can never be withdrawn, and the `main` guard ignores lease expiry, so a single bad or duplicate participant submission can leave a base with no honest publication path (findings 1 and 3). Operationally, the worker has no ordering, partitioning, or permanent-failure classification, so cancelled drafts awaiting cleanup can starve verification for a day and multiple workers only duplicate S3 reads (findings 2, 7, 8), and the one unconditional state write in `complete_upload` can regress a blob that another process already advanced (finding 4). The test suite runs on SQLite whose BEGIN IMMEDIATE serializes everything, so none of the PostgreSQL lock-scope questions, the two-API/two-worker interleavings, or the >256-row worker batching behavior are exercised; I would fix findings 1 and 2 and add a PostgreSQL-backed concurrency test before building automated multi-coordinator flows on this backend.

**sdk**: Through the SDK/adapter/command lens the exchange backend is a well-structured control plane with a client integration that has not been exercised against failure. The claim mechanism is the sharpest problem: because the owner command runs non-skippable validation after freezing inputs, has no way to release a claim, and the server blocks every other route to `main` for a claimed base, a single incompatible checkpoint, allowlist miss, or oversize round record wedges the space until someone edits the database. The resume story is effectively non-functional from the CLI (the fingerprint hashes a timestamp the client rewrites on every run), which turns every transient upload failure into an undocumented manual cleanup and a quota-leaking orphan draft; the lack of control-plane retries, a shared hard-coded upload+verify deadline, and partial-deletion on download exhaustion compound this. Immutable, undeletable submissions also mean a participant's duplicate submit permanently disables automatic and claim modes for that round. None of this is caught because the SDK and adapter have no offline tests and the live test covers only one clean round; I would block on the claim-release gap and the fingerprint bug before building further on this backend.

**drift**: Through the design-versus-implementation lens, the core generic exchange (spaces, memberships, records, blobs, CAS references, cursor pagination, transactional events, worker reconciliation) tracks docs/EXCHANGE_SERVICE_DESIGN.md sections 1-6 closely and honors the important invariants (version pinning, no storage I/O under DB locks, server-derived creator/participant, same-space FKs). The drift concentrates in section 7 and the "generic vs. FL profile" boundary: the claim mechanism the design calls an optional extension is hardcoded into the generic ref path with literal kind names, and it introduces two states the design did not intend -- a claim that permanently pins `main` for its base with no abandonment API, and a duplicate-participant hard failure with no withdrawal flag -- both of which strand a live FedAvg round without DB surgery. Several designed tables and admin capabilities (audit, principals, mutable space policy/quota, idempotency retention) are absent and, unlike the pull-only event feed and manual space creation, are not disclosed in EXCHANGE_SERVICE.md. Test coverage of the control plane is solid, but the SDK and ModelStore adapter -- where the section 9 resume and end-to-end acceptance cases live -- run only against a live S3 endpoint even though the test extra already ships moto's HTTP server. Overall this is a credible v1 control plane whose docs should be corrected to list the omitted resources, and whose claim lifecycle should be fixed before the exchange backend is relied on for automated multi-coordinator rounds.

**operability**: Through the operability/scalability/data-model lens the exchange backend is a coherent, well-reasoned control plane whose consistency story (space-row lock ordering, two-phase S3 initiation, recoverable worker transitions) is sound and multi-process-safe, but it has not yet been engineered for load or for running in production. The single most consequential design choice is that Service.transaction() takes FOR UPDATE on the space row for every request including reads and grant issuance, which serializes each space's traffic, ties up the default 15-connection pool, and is compounded by N+1 serialization inside the lock, so the ops doc's implication that PostgreSQL is the "scale-out" configuration is not currently accurate. Observability is effectively absent: no logging module is used, request IDs are returned but never recorded, storage and database failures collapse into a 503/500 or an anonymous `retry` counter, and unhandled DB errors break the JSON error contract; the verification worker is single-threaded with no work claiming, so it neither scales nor tolerates a second instance efficiently. The schema diverges from the design document in ways that will each require a migration the project does not yet have tooling for (SERIAL event IDs, float wall-clock timestamps, JSON instead of JSONB, missing composite/creator indexes, an idempotency table with no retention column), and tables grow without bound. Before building further, I would fix the read-path locking, add structured logging with request IDs and DB-error handling, add worker claiming/concurrency, and land an initial Alembic migration that corrects the column types and indexes while the tables are still empty.

**tests**: The offline suite (12 tests, ~3.5 s, SQLite + moto in-process) is well structured for a first cut: it uses real RS256 tokens, real S3 emulation, per-test isolated buckets and databases, and drives most control-plane paths through the HTTP API rather than by poking the ORM. However, its discriminating power is much weaker than its test names suggest: I empirically confirmed that disabling JWT signature verification, removing the Space row lock, removing the events visibility filter, making S3 cleanup a no-op, and deleting the aggregate_base_mismatch guard each leave the relevant tests (and in the last case the entire suite) green. Every assertion checks only HTTP status, never the documented stable error code, which is why guards sharing a 409/404/412 are interchangeable to the suite. The largest structural gap is that the client SDK, the ExchangeStore adapter, the upload resume path (GET /uploads, parts:authorize success, complete failure, abort), the claim lifecycle endpoints (GET/renew/replay), and custom JSON-schema rules have zero offline coverage, even though moto[server] is declared and I verified it serves presigned part PUTs and ranged GETs, so all of this is testable today without live infrastructure. Highest-value additions, in order: wrong-key/alg-confusion auth negatives; a moto-server-backed SDK upload/resume/download test that also runs the FedAvg e2e; explicit aggregate_base_mismatch and claim-replay tests asserting body codes; authorization-matrix negatives with reader-only, admin-only, second-space and private-blob-download cases; and running the suite against PostgreSQL in CI so the concurrency test means something.

**opsdoc**: Through the operations-guide-accuracy lens, docs/EXCHANGE_SERVICE.md is largely faithful to the code on the surface it chooses to describe: install extras, environment variables and their validation, token requirements (typ, RS256, iss/aud/sub/iat/exp, scope), CLI verbs, default kinds and visibility, the 1 MiB / 64 KiB / 256-attachment limits, 24h draft expiry, 5-minute grants, and the SQLite/Moto vs. live test switches all match. The serious problems are omissions rather than wrong statements: the claim workflow the guide recommends for automation has no abandon/cancel path, so one non-aggregatable frozen input wedges `main` for that base with no sane API recovery, and the guide's 'expected control conditions' list does not disclose this or the `duplicate_participant` dead end. Two adapter-level bugs directly undercut documented behavior: the FL adapter's derived resume state file can never match on retry because the manifest embeds a fresh timestamp, and a single malformed ready `training.update` aborts every `--discover-submissions` run because the mismatch check sits outside the skip block. Smaller inaccuracies include a missing `s3:GetBucketVersioning` permission that breaks least-privilege startup, quota/rules being immutable despite the design table, blanket `$ref` rejection contradicting 'local JSON Schemas', and undocumented `Idempotency-Key` requirements. A principal engineer should block further FedAvg automation on the claim-recovery gap and the retry/resume bug before building on this backend.

**architecture**: The service boundary is drawn in a defensible place (authenticated JSON control plane, direct-to-S3 versioned blobs, worker-side SHA-256 given S3's lack of full-object SHA-256 for multipart), and the low-level recoverability work (reserved keys, pinned versions, CAS refs, lost-response reconciliation) is genuinely careful. The architectural weakness is above that layer: the claim/fence model freezes inputs server-side while validation stays in the owner, and has no abandon or re-freeze path, so an ordinary FL condition (one bad checkpoint, one participant retry, one ref move) wedges `main` with no API-level recovery; the FL profile is hardcoded by magic kind/ref names inside the generic service rather than configured; and the record lifecycle stops at 'ready' with no withdrawal, no policy mutation, no quota reclamation, and no space mutation, making every space a monotonically filling bucket whose quota cannot be raised. Every request also takes an exclusive per-space row lock, which the SQLite tests cannot reveal and which caps PostgreSQL throughput per space. Before building further I would require: coordinator-supplied claim inputs plus a claim abandon route, kind-rule-driven profile configuration, an admin surface for quota/policy/retention, read paths without `FOR UPDATE`, and the `ModelStore` generation/claim contract change the design document itself specified.
