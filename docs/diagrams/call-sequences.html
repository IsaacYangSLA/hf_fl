CALL SEQUENCE / UPLOAD

Upload & publish

Small metadata requests go to the service. Large files go directly to private blob storage, including retries after a lost response. The worker verifies each stored version before the client publishes its record.

100%
Mermaid source
sequenceDiagram
    autonumber
    actor App as Client application
    participant SDK as Exchange SDK
    participant API as API and service
    participant DB as Metadata database
    participant Worker as Transfer worker
    participant S3 as Versioned blob storage

    Note over App,S3: Prerequisites: external IdP access token, space membership, registered type and policy, versioned bucket
    Note over SDK,API: All control requests carry Bearer JWT, API validates signature, issuer, audience, expiry and exchange scope<br/>Service checks current membership and applicable ownership, roles and policy
    Note over SDK,API: Route prefixes: R = /v2/spaces/{space}/records, A = R/{record}/attachments/{attachment}
    App->>SDK: put_record(metadata, files, schema_revision_id, state_path)
    SDK->>SDK: Hash regular files and retain operation identity and keys
    SDK->>API: POST R with metadata, attachment sizes and SHA-256, idempotency key
    API->>DB: Validate schema, policy and quotas, commit draft, reservations and event
    API-->>SDK: Draft record and attachment descriptors
    SDK->>API: GET R/{record}
    API-->>SDK: Authorized draft and attachment states

    loop Each attachment needing upload
        SDK->>API: POST A/upload
        API->>DB: Authorize owner and draft, reserve attempt with private storage key
        API->>S3: CreateMultipartUpload
        S3-->>API: UploadId
        API->>DB: Commit uploading state and upload handle
        API-->>SDK: Uploading state, protocol and part size
        SDK->>API: GET A/parts
        API->>S3: ListParts after ownership and state checks
        API-->>SDK: Existing part numbers, ETags and sizes
        SDK->>SDK: Resume parts whose number and expected size match
        loop Each missing or wrong-size part
            SDK->>API: POST A/grants with part number
            API->>API: Sign expiring UploadPart URL with expected Content-Length
            API->>DB: Recheck authorization and state, retain actual grant expiry
            API-->>SDK: Signed URL and required headers
            SDK->>S3: PUT part bytes directly using signed URL
            alt Successful response received
                S3-->>SDK: Part upload result
            else Provider accepted bytes, but response was lost
                S3--xSDK: Successful response lost in transit
                SDK->>API: POST A/grants again for the same part number
                API->>API: Sign a fresh grant for the same expected length
                API->>DB: Recheck authorization and state, retain grant expiry
                API-->>SDK: Fresh signed URL and required headers
                SDK->>S3: Retry the same part number and bytes
                S3->>S3: Replace that logical part and its ETag
                S3-->>SDK: Part upload result
            end
        end
        Note over SDK,S3: The SDK bounds PUT retries and the upload deadline, retries obtain fresh grants<br/>S3 must expose one latest part per number, SeaweedFS 4.47 needs the pinned single-gateway compatibility build
        SDK->>SDK: Recheck source size and SHA-256
        SDK->>API: POST A/complete
        API->>DB: Authorize and mark completing with mutation token
        API->>S3: HEAD private attempt key, then ListParts if no completed object
        S3-->>API: Current logical parts and their ETags
        API->>API: Require exact count, contiguous unique numbers and expected sizes
        API->>S3: CompleteMultipartUpload with listed ETags
        S3-->>API: Stored object VersionId
        API->>DB: Commit verifying state and VersionId
        API-->>SDK: 202 with attachment state
    end

    Note over SDK,Worker: SDK may retry POST R/{record}/publish, receive 409 attachments_not_verified,<br/>GET the record and sleep while verification is pending
    Worker->>DB: Select due verification work, recheck category, acquire lease
    Worker->>S3: GET exact object VersionId and stream bytes
    Worker->>Worker: Compare actual size and SHA-256 with declared values
    Worker->>DB: If lease still owned, commit verified binding and event
    Note over DB,Worker: Verification marks attachments verified, the record is still a draft
    SDK->>API: POST R/{record}/publish with persisted idempotency key
    API->>DB: Recheck policy and verified attachments, commit published record and event
    API-->>SDK: Published record
    SDK-->>App: RecordDescriptor

    Note over App,S3: A lost successful PUT response is shown, other failures and cleanup use separate recovery paths<br/>Large client uploads bypass the API, exact-version worker verification still checks all stored bytes

CALL SEQUENCE / DOWNLOAD

Read & download

The service checks current access and returns metadata or a short-lived download grant. The client reads the pinned object version directly and verifies the downloaded bytes.

100%
Mermaid source
sequenceDiagram
    autonumber
    actor App as Client application
    participant SDK as Exchange SDK
    participant API as API and service
    participant DB as Metadata database
    participant S3 as Versioned blob storage

    Note over App,S3: Prerequisites: external IdP access token and current membership with access to a published record
    Note over SDK,API: Route prefixes: R = /v2/spaces/{space}/records, A = R/{record}/attachments/{attachment}
    App->>SDK: get_record(space, record_id)
    SDK->>API: GET R/{record} with Bearer JWT
    API->>API: Authenticate JWT and required exchange scope
    API->>DB: Check current membership and record visibility, read metadata
    API-->>SDK: Metadata and attachment descriptors including size and SHA-256
    SDK-->>App: RecordDescriptor
    App->>SDK: download_attachment(space, record_id, attachment, output)
    Note over App,SDK: SDK can return immediately if an existing local file already matches size and SHA-256

    loop Initial transfer or bounded retry after interruption
        SDK->>API: GET A/download with Bearer JWT
        API->>API: Authenticate JWT and required exchange scope
        API->>DB: Check membership and visibility, require published record and verified attachment
        DB-->>API: Storage key, verified VersionId, size and SHA-256
        API->>API: Locally sign expiring GetObject URL bound to verified VersionId
        Note right of API: Use explicit Exchange S3 credentials with any configured session token,<br/>or boto3's AWS credential provider chain and supported refresh<br/>Temporary credentials include their session token in the signed URL
        API->>DB: Recheck authorization and states, retain grant expiry
        API-->>SDK: Signed URL, headers, expiry, size and SHA-256
        SDK->>SDK: Check grant descriptor against expected attachment
        SDK->>S3: GET signed URL, Range header if resuming partial file
        S3-->>SDK: 200 response or 206 response with Content-Range and bytes
        SDK->>SDK: Validate 206 range against offset and expected total size
        SDK->>SDK: Stream into partial file within size and time bounds<br/>Append valid 206 bytes, restart local file on 200
    end
    SDK->>SDK: Verify final size and SHA-256, replace destination with completed file
    SDK-->>App: Local file path

    Note over SDK,S3: Blob requests use signed grants without the Exchange Bearer token<br/>New grants require current authorization, membership changes do not revoke an issued grant<br/>A grant can stop working before its signed expiry if the signing credentials expire or are revoked
    Note over App,S3: Successful download path shown, authentication failures and integrity errors stop the operation

CALL SEQUENCE / WORKER

Worker & cleanup

Cancellation can change an attempt after a worker selects it. Acquisition rechecks its category under the lifecycle lock, so cleanup runs through the cleanup pool when it becomes eligible.

100%
Mermaid source
sequenceDiagram
    autonumber
    actor Client as Record owner
    participant API as API and service
    participant Tick as Worker tick
    participant Verify as Verification pool
    participant Cleanup as Cleanup pool
    participant DB as Metadata database
    participant S3 as Versioned blob storage

    Note over Tick,S3: Independent thread pools reserve verification and cleanup capacity<br/>Storage I/O runs outside database transactions, an acquired attempt is a detached state snapshot
    Tick->>DB: expire(batch), then work(batch)
    DB-->>Tick: Due verifying attempt T in verification list
    Note over Tick,DB: Verification list includes initiating, completing and verifying states<br/>Both lists require next_attempt due and no active lease, cleanup also requires expired grants
    Tick->>Verify: Submit process(T, cleanup=false)

    Note over Client,Verify: Example race: cancellation commits after selection, before lease acquisition
    Client->>API: DELETE /v2/spaces/{space}/records/{record}
    API->>DB: Authorize and lock Space for lifecycle transaction
    API->>DB: Cancel draft, move attempt T to cleanup<br/>Move byte charge from allocated to reclaiming
    Note over API,DB: Retain active ownership and delay cleanup until existing grants expire
    API-->>Client: Record state cancelled

    Verify->>DB: acquire(T, cleanup=false), lock Space, refresh attempt
    DB-->>Verify: Current state cleanup does not match selected category
    Verify->>Verify: Return skipped without leasing, mutating or calling storage
    Verify-->>Tick: skipped
    Note over Verify,Cleanup: The symmetric check skips verification states dispatched to cleanup<br/>If cancellation happens after acquisition, verification may finish its GET,<br/>but its state-checked commit is rejected, it never switches to cleanup I/O
    Tick->>Tick: Wait for all submitted futures, then prune history
    Note over Tick,Cleanup: Pools are independent within a finite batch<br/>A tick waits for both pools before selecting the next batch

    Tick->>DB: Later tick: select T when retry time, lease and grant gates permit
    DB-->>Tick: T in cleanup list
    Tick->>Cleanup: Submit process(T, cleanup=true)
    Cleanup->>DB: acquire(T, cleanup=true), lock Space, refresh attempt<br/>Recheck category and due gates, commit lease token
    DB-->>Cleanup: Leased cleanup snapshot
    Note over Cleanup,DB: Heartbeat renews only the matching unexpired lease during provider I/O
    Cleanup->>S3: ListMultipartUploads at T's private key, abort matching uploads
    Cleanup->>S3: ListParts must confirm each aborted upload is gone
    Cleanup->>S3: ListObjectVersions, delete matching versions and delete markers
    S3-->>Cleanup: Cleanup calls completed
    Cleanup->>DB: commit(cleaned), lock Space and attempt<br/>Require current token, live lease and matching state
    alt Lease ownership or current state no longer matches
        DB-->>Cleanup: Reject stale result without finalizing cleanup
        Cleanup-->>Tick: skipped
    else Outstanding storage mutation markers remain
        DB-->>Cleanup: Retain cleanup and reclaiming charge, schedule retry
        Cleanup-->>Tick: skipped
    else Ownership valid and mutations settled
        DB-->>Cleanup: Commit cleaned and event<br/>Release reclaiming charge when all blob attempts are cleaned
        Cleanup-->>Tick: cleaned
    end
    Note over Cleanup,S3: Provider failures retry cleanup, a database lease cannot cancel outstanding storage mutations<br/>Mutation markers prevent premature cleanup finalization and quota release

CALL SEQUENCE / FEDAVG

Federated round

Two participants train from one immutable global base. The owner acquires or resumes frozen inputs, saves ownership before metadata reads, then validates and averages updates and advances main through a fenced acquisition.

100%
Mermaid source
sequenceDiagram
    autonumber
    actor C as Clients A and B
    actor O as Owner
    participant R as FedAvgRunner
    participant S as ExchangeStore / SDK
    participant X as Exchange API
    participant D as SQL database

    Note over C,D: Prerequisites: configured fedavg.v1 space and memberships,<br/>registered types, published global base and initialized main.<br/>All clients use the same immutable base record ID.
    Note over S,X: Separate adapter / SDK per caller.<br/>API calls use bearer authentication.<br/>Route prefix: /v2/spaces/{space}

    loop Each independent client, at least two
        Note over C,S: Clients may run concurrently.<br/>Each starts from the shared global base.
        C->>S: download_client_round() uses<br/>download_snapshot(base_id)
        Note over C,X: Read metadata and download attachments.<br/>See download diagram.<br/>Validate round manifest and supplied hashes.
        S-->>C: Base checkpoint + client context
        C->>C: Train locally<br/>Build update manifest + hashes
        C->>S: upload_client_update() uses<br/>publish_submission(base_revision=base_id)
        Note over S,X: _publish(kind=training.update)<br/>calls put_record().<br/>See upload diagram.
        S-->>C: Published update record ID<br/>main remains unchanged
    end

    O->>R: run(selection=claim,<br/>publish=true)
    R->>S: resolve_reference(main)
    S->>X: GET /refs/main
    X-->>S: Base ID + generation token
    S-->>R: ResolvedReference(base_id, token)
    R->>S: download_snapshot(base_id)<br/>Round manifest only
    S->>X: GET /records/{base_id}
    X-->>S: Published record<br/>Inline round metadata
    S-->>R: fedavg_round.json
    R->>R: Read or persist round and key<br/>under run-state lock
    R->>S: acquire_claim(context,<br/>acquisition_key)
    alt Saved or explicitly selected claim ID
        S->>X: GET /acquisitions/{id}
        X-->>S: Acquisition state and frozen IDs
        S->>S: Require matching reference<br/>and active state before renewal
        S->>X: POST /acquisitions/{id}/renew<br/>fence, proves current ownership
        X-->>S: Renewed acquisition or error
        Note over S,X: Inactive renewal triggers another GET<br/>to distinguish a completion race<br/>from confirmed lost ownership.
    else New acquisition or key-only replay
        S->>X: POST /acquisitions<br/>main + expected_token<br/>input_record_ids=[]<br/>Persisted idempotency key
        X->>D: Transaction: authorize publisher<br/>Check reference generation<br/>Newest eligible update per participant<br/>Require at least 2, freeze IDs<br/>Persist holder, fence and lease
        D-->>X: Acquisition committed or replayed
        X-->>S: Acquisition state<br/>Frozen input IDs
    end
    Note over R,X: Changed round or completed acquisition stops recovery.<br/>Uncertain outcomes retain evidence for reconciliation.<br/>An explicitly selected claim is never replaced.
    opt Confirmed inactive nonpublication, no explicit claim ID
        S-->>R: ClaimInactive
        R->>R: Persist new key<br/>Remove saved claim ownership
        R->>S: acquire_claim() with new key
        S->>X: POST /acquisitions<br/>Same round, new idempotency key
        X->>D: Recheck base and eligibility<br/>Freeze a new acquisition
        X-->>S: New active acquisition
    end
    S-->>R: ClaimHandle with frozen input IDs
    R->>R: Persist claim ID, fence and lease<br/>Start ClaimRenewal thread

    par Background renewal until publication or exit
        loop While the claim is held
            R->>S: renew_claim(claim)
            S->>X: POST /acquisitions/{id}/renew<br/>fence
            X->>D: Check holder, lease and fence<br/>Extend lease
            X-->>S: Renewed acquisition
            S-->>R: Updated ClaimHandle<br/>Persist run-state
        end
    and Owner processes the frozen candidates
        R->>S: explicit_submissions(input_ids)
        loop Each frozen input
            S->>X: GET /records/{input_id}
            X-->>S: Published training.update descriptor
        end
        S-->>R: Frozen candidates
        Note over R,X: Metadata failures reach the runner with saved ownership.<br/>Confirmed abandon clears run-state, failed abandon retains it.
        R->>S: Resolve inputs<br/>Download submission manifests
        S-->>R: Immutable IDs<br/>Participant-bound metadata
        R->>R: Validate base, round and participant<br/>Check algorithm, require at least 2
        Note over R,X: Download base and candidate attachments.<br/>Check checkpoint compatibility and schema-2 hashes.<br/>Owner ignores schema-1 supplied hashes.<br/>Require at least 2 valid checkpoints after filtering.
        R->>R: Compute coefficients, reduce shards<br/>Optionally evaluate<br/>Write round manifest + hashes
        R->>S: publish_aggregate(reference,<br/>claim, used input IDs)
        Note over S,X: _publish(kind=model.global)<br/>uses the upload lifecycle.<br/>Published record precedes main update.
        S->>X: POST /acquisitions/{id}/complete<br/>fence + result_record_id<br/>Idempotency-Key:<br/>aggregate-{record_id}
        X->>D: Atomic transaction:<br/>Check holder, lease, fence, generation<br/>Validate provenance and membership<br/>Advance main and generation<br/>Complete acquisition
        D-->>X: Reference and acquisition committed
        X-->>S: Completed acquisition
        opt A tag was requested
            S->>X: PUT /refs/{tag}<br/>If-None-Match: *
            X-->>S: Tag created or warning<br/>Main remains published
        end
        S-->>R: PublishResult
    end

    R->>R: Stop renewal, clear run-state<br/>Write result.json
    R-->>O: RoundResult(status=published)
    Note over O,X: Ambiguous completion raises PublicationUncertain.<br/>Run-state is retained for reconciliation.<br/>The owner launches aggregation, not the service.

Reading the diagrams

Solid arrows are calls; dashed arrows are responses. Notes group prerequisites and intentional omissions. Routes are relative to the space prefix identified in each diagram. The API lane includes authentication, transactional application commands, and transfer orchestration.

Scope and current limitations

These views cover the independent Exchange backend, multipart retry, cancellation and worker isolation, and owner-controlled FedAvg with acquisition recovery. Identity provisioning, HF/JFrog transports, and the complete failure state machine are outside this view. Existing implementation gaps remain: see the v3 limitations and service runbook.
