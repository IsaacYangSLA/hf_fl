CALL SEQUENCE / UPLOAD

Upload & publish

Small metadata requests go to the service. Large files go directly to private blob storage. The worker verifies each stored version before the client publishes its record.

100%
Mermaid source
sequenceDiagram
    autonumber
    actor App as Client application
    participant SDK as Exchange SDK
    participant API as API and service
    participant DB as Metadata database
    participant Worker as Transfer worker
    participant S3 as Versioned blob storage

    Note over App,S3: Prerequisites: external IdP access token, space membership, registered type and policy, versioned bucket
    Note over SDK,API: All control requests carry Bearer JWT, API validates signature, issuer, audience, expiry and exchange scope<br/>Service checks current membership and applicable ownership, roles and policy
    Note over SDK,API: Route prefixes: R = /v2/spaces/{space}/records, A = R/{record}/attachments/{attachment}
    App->>SDK: put_record(metadata, files, schema_revision_id, state_path)
    SDK->>SDK: Hash regular files and retain operation identity and keys
    SDK->>API: POST R with metadata, attachment sizes and SHA-256, idempotency key
    API->>DB: Validate schema, policy and quotas, commit draft, reservations and event
    API-->>SDK: Draft record and attachment descriptors
    SDK->>API: GET R/{record}
    API-->>SDK: Authorized draft and attachment states

    loop Each attachment needing upload
        SDK->>API: POST A/upload
        API->>DB: Authorize owner and draft, reserve attempt with private storage key
        API->>S3: CreateMultipartUpload
        S3-->>API: UploadId
        API->>DB: Commit uploading state and upload handle
        API-->>SDK: Uploading state, protocol and part size
        SDK->>API: GET A/parts
        API->>S3: ListParts after ownership and state checks
        API-->>SDK: Existing part numbers and sizes
        loop Each missing part
            SDK->>API: POST A/grants with part number
            API->>API: Sign expiring UploadPart URL with expected Content-Length
            API->>DB: Recheck authorization and state, retain actual grant expiry
            API-->>SDK: Signed URL and required headers
            SDK->>S3: PUT bytes directly using signed URL
            S3-->>SDK: Part upload result
        end
        SDK->>SDK: Recheck source size and SHA-256
        SDK->>API: POST A/complete
        API->>DB: Authorize and mark completing with mutation token
        API->>S3: Check object and parts, CompleteMultipartUpload
        S3-->>API: Stored object VersionId
        API->>DB: Commit verifying state and VersionId
        API-->>SDK: 202 with attachment state
    end

    Note over SDK,Worker: SDK may retry POST R/{record}/publish, receive 409 attachments_not_verified,<br/>GET the record and sleep while verification is pending
    Worker->>DB: Select due attempts, acquire database lease
    Worker->>S3: GET exact object VersionId and stream bytes
    Worker->>Worker: Compare actual size and SHA-256 with declared values
    Worker->>DB: If lease still owned, commit verified binding and event
    Note over DB,Worker: Verification marks attachments verified, the record is still a draft
    SDK->>API: POST R/{record}/publish with persisted idempotency key
    API->>DB: Recheck policy and verified attachments, commit published record and event
    API-->>SDK: Published record
    SDK-->>App: RecordDescriptor

    Note over App,S3: Normal successful path shown, upload retries, failed verification and cleanup are omitted<br/>Large client uploads bypass the API, the worker reads stored bytes to verify them

CALL SEQUENCE / DOWNLOAD

Read & download

The service checks current access and returns metadata or a short-lived download grant. The client reads the pinned object version directly and verifies the downloaded bytes.

100%
Mermaid source
sequenceDiagram
    autonumber
    actor App as Client application
    participant SDK as Exchange SDK
    participant API as API and service
    participant DB as Metadata database
    participant S3 as Versioned blob storage

    Note over App,S3: Prerequisites: external IdP access token and current membership with access to a published record
    Note over SDK,API: Route prefixes: R = /v2/spaces/{space}/records, A = R/{record}/attachments/{attachment}
    App->>SDK: get_record(space, record_id)
    SDK->>API: GET R/{record} with Bearer JWT
    API->>API: Authenticate JWT and required exchange scope
    API->>DB: Check current membership and record visibility, read metadata
    API-->>SDK: Metadata and attachment descriptors including size and SHA-256
    SDK-->>App: RecordDescriptor
    App->>SDK: download_attachment(space, record_id, attachment, output)
    Note over App,SDK: SDK can return immediately if an existing local file already matches size and SHA-256

    loop Initial transfer or bounded retry after interruption
        SDK->>API: GET A/download with Bearer JWT
        API->>API: Authenticate JWT and required exchange scope
        API->>DB: Check membership and visibility, require published record and verified attachment
        DB-->>API: Storage key, verified VersionId, size and SHA-256
        API->>API: Sign expiring GetObject URL bound to VersionId
        API->>DB: Recheck authorization and states, retain grant expiry
        API-->>SDK: Signed URL, headers, expiry, size and SHA-256
        SDK->>SDK: Check grant descriptor against expected attachment
        SDK->>S3: GET signed URL, Range header if resuming partial file
        S3-->>SDK: 200 or validated 206 response with bytes
        SDK->>SDK: Stream into local partial file within size and time bounds
    end
    SDK->>SDK: Verify final size and SHA-256, replace destination with completed file
    SDK-->>App: Local file path

    Note over SDK,S3: Blob requests use signed grants without the Exchange Bearer token<br/>New grants require current authorization, already issued grants remain usable until expiry
    Note over App,S3: Successful download path shown, authentication failures and integrity errors stop the operation

CALL SEQUENCE / FEDAVG

Federated round

Two participants train from one immutable global base. The owner freezes eligible updates, validates and averages them, then advances main through a fenced acquisition.

100%
Mermaid source
sequenceDiagram
    autonumber
    actor C as Clients A and B
    actor O as Owner
    participant R as FedAvgRunner
    participant S as ExchangeStore / SDK
    participant X as Exchange API
    participant D as SQL database

    Note over C,D: Prerequisites: configured fedavg.v1 space and memberships,<br/>registered types, published global base and initialized main.<br/>All clients use the same immutable base record ID.
    Note over S,X: Separate adapter / SDK per caller.<br/>API calls use bearer authentication.<br/>Route prefix: /v2/spaces/{space}

    loop Each independent client, at least two
        Note over C,S: Clients may run concurrently.<br/>Each starts from the shared global base.
        C->>S: download_client_round() uses<br/>download_snapshot(base_id)
        Note over C,X: Read metadata and download attachments.<br/>See download diagram.<br/>Validate round manifest and supplied hashes.
        S-->>C: Base checkpoint + client context
        C->>C: Train locally<br/>Build update manifest + hashes
        C->>S: upload_client_update() uses<br/>publish_submission(base_revision=base_id)
        Note over S,X: _publish(kind=training.update)<br/>calls put_record().<br/>See upload diagram.
        S-->>C: Published update record ID<br/>main remains unchanged
    end

    O->>R: run(selection=claim,<br/>publish=true)
    R->>S: resolve_reference(main)
    S->>X: GET /refs/main
    X-->>S: Base ID + generation token
    S-->>R: ResolvedReference(base_id, token)
    R->>S: download_snapshot(base_id)<br/>Round manifest only
    S->>X: GET /records/{base_id}
    X-->>S: Published record<br/>Inline round metadata
    S-->>R: fedavg_round.json
    R->>R: Persist round and acquisition key<br/>under run-state lock
    R->>S: acquire_claim(context,<br/>acquisition_key)
    S->>X: POST /acquisitions<br/>main + expected_token<br/>input_record_ids=[]<br/>Persisted idempotency key
    X->>D: Transaction: authorize publisher<br/>Check reference generation<br/>Newest eligible update per participant<br/>Require at least 2, freeze IDs<br/>Persist holder, fence and lease
    D-->>X: Acquisition committed
    X-->>S: Active acquisition<br/>Frozen input IDs
    S-->>R: ClaimHandle with frozen input IDs
    R->>R: Persist claim ID, fence and lease<br/>Start ClaimRenewal thread

    par Background renewal until publication or exit
        loop While the claim is held
            R->>S: renew_claim(claim)
            S->>X: POST /acquisitions/{id}/renew<br/>fence
            X->>D: Check holder, lease and fence<br/>Extend lease
            X-->>S: Renewed acquisition
            S-->>R: Updated ClaimHandle<br/>Persist run-state
        end
    and Owner processes the frozen candidates
        R->>S: explicit_submissions(input_ids)
        loop Each frozen input
            S->>X: GET /records/{input_id}
            X-->>S: Published training.update descriptor
        end
        S-->>R: Frozen candidates
        Note over R,X: Metadata failures reach the runner with saved ownership.<br/>Confirmed abandon clears run-state, failed abandon retains it.<br/>Without an explicit claim ID, confirmed inactive attempts can restart.<br/>Completed or uncertain publication requires reconciliation.
        R->>S: Resolve inputs<br/>Download submission manifests
        S-->>R: Immutable IDs<br/>Participant-bound metadata
        R->>R: Validate base, round and participant<br/>Check algorithm, require at least 2
        Note over R,X: Download base and candidate attachments.<br/>Check checkpoint compatibility and schema-2 hashes.<br/>Owner ignores schema-1 supplied hashes.<br/>Require at least 2 valid checkpoints after filtering.
        R->>R: Compute coefficients, reduce shards<br/>Optionally evaluate<br/>Write round manifest + hashes
        R->>S: publish_aggregate(reference,<br/>claim, used input IDs)
        Note over S,X: _publish(kind=model.global)<br/>uses the upload lifecycle.<br/>Published record precedes main update.
        S->>X: POST /acquisitions/{id}/complete<br/>fence + result_record_id<br/>Idempotency-Key:<br/>aggregate-{record_id}
        X->>D: Atomic transaction:<br/>Check holder, lease, fence, generation<br/>Validate provenance and membership<br/>Advance main and generation<br/>Complete acquisition
        D-->>X: Reference and acquisition committed
        X-->>S: Completed acquisition
        opt A tag was requested
            S->>X: PUT /refs/{tag}<br/>If-None-Match: *
            X-->>S: Tag created or warning<br/>Main remains published
        end
        S-->>R: PublishResult
    end

    R->>R: Stop renewal, clear run-state<br/>Write result.json
    R-->>O: RoundResult(status=published)
    Note over O,X: Ambiguous completion raises PublicationUncertain.<br/>Run-state is retained for reconciliation.<br/>The owner launches aggregation, not the service.

Reading the diagrams

Solid arrows are calls; dashed arrows are responses. Notes group prerequisites and intentional omissions. Routes are relative to the space prefix identified in each diagram. The API lane includes authentication, transactional application commands, and transfer orchestration.

Scope and current limitations

These views cover the independent Exchange backend and a successful owner-controlled FedAvg round. Identity provisioning, HF/JFrog transports, and failure/cleanup paths are outside this view. Existing implementation gaps remain: see the v3 limitations and service runbook.
