# Architecture review: hf2l at 714fd66

Principal-engineer review of the `hf2l` repository (Hugging Face / JFrog / custom-exchange federated-learning proof of concept), commit `714fd66`. Lens: how to make the codebase more general (new FL algorithms, model frameworks and checkpoint formats, storage backends, identity providers, deployment shapes) and easier to maintain (layering, small stable interfaces, no duplicated logic, consistent error/config/logging conventions, testability, docs that match code). Sections 5-8 (design, plan, alternatives, open questions) were rewritten after the owner removed the backward-compatibility and migration constraint (see Method); sections 3-4 are unchanged from the first revision. References to "step 1" in sections 3-4 predate the plan rewrite and correspond to WP1, which deletes `hf2l/hub_helpers.py`, the target of all three inverted imports.

All `path:line` references were checked against HEAD while writing this document. Counts (tests, routes, error codes, print sites) were derived from the tree, not copied from earlier notes.

## Summary

**What the system is.** `hf2l` is a ~5,400-line (~4,800 non-blank; `git ls-files 'hf2l/*.py'`) Python package with two deployables. (1) A set of seven argparse CLIs (`pyproject.toml:49-56`) that implement synchronous FedAvg over a "versioned model repository" abstraction: clients download a pinned base, train with any local code or a trusted plugin, and upload a SafeTensors checkpoint plus a `fedavg_submission.json` manifest; an owner discovers or claims submissions, verifies hashes and tensor schemas, streams a weighted average shard by shard, writes `fedavg_round.json`, and publishes to `main` under a compare-and-swap guard. The repository abstraction (`ModelStore`, `hf2l/backends/base.py:37-132`) has three implementations: Hugging Face Hub (PR refs), JFrog Artifactory (named revisions, AQL discovery) and an in-house exchange. (2) The exchange service (`hf2l/exchange/`, FastAPI + SQLAlchemy + S3 + RS256 JWT): spaces, membership, records with JSON-Schema metadata, presigned multipart blob uploads, CAS references, an event cursor and fenced work claims, plus a recovery worker and an httpx SDK. A GitHub Actions workflow and a webhook relay automate the Hugging Face owner path.

**The seven most important structural findings.**

1. FedAvg is control flow and constants at every layer, not a strategy. Weighting is an inline `if/else` (`hf2l/owner_fedavg.py:414-418`), the algorithm is a free-text string (`:448`), the quorum is a literal in three places (`:356`, `:364`; `hf2l/exchange/schemas.py:123`; `.github/workflows/fed_avg.yml:58`), and the exchange dereferences `MAIN_REF`/`UPDATE_KIND`/`PROVENANCE_FIELD` in a dozen handlers (`hf2l/exchange/api.py:371-378, 395-417, 664-665, 903-905, 940, 1043-1050`). FedProx, Scaffold, secure aggregation and async FL each require forking `main()` and editing the generic service.
2. Layering is inverted at the protocol seam. The "standard library only" wire module imports FedAvg manifest names (`hf2l/exchange/protocol.py:1` vs `:5`), the exchange adapter parses and rebuilds the round record (`hf2l/backends/exchange.py:22-23, 41-70, 326`), JFrog queries the literal `fedavg_submission.json` in AQL (`hf2l/backends/jfrog.py:198`), and kinds/states/codes/routes are re-spelled as literals in server, SDK, adapter and tests with nothing linking them.
3. `ModelStore` is a FedAvg-round-shaped fat ABC with no capability model. Seven abstract methods carry participant/round/claim vocabulary; implementations `del` parameters they cannot use (`hf2l/backends/huggingface.py:82`, `jfrog.py:183, 293`); the owner and client steps infer behaviour from backend names in eight places (`owner_fedavg.py:77, 231, 237, 241, 266, 336, 500`; `hf2l/client_steps.py:73`); the factory is a closed tuple plus if-chain with eager imports (`hf2l/backends/factory.py:10-11, 17, 40-67`).
4. The owner round pipeline is a 291-line CLI monolith (`owner_fedavg.py:222-512`) with no callable API, no typed result, 22 `print()` sites, one `except Exception` that maps every failure to exit 1 (`:504-512`), and a workspace rule (`:249`) that makes the adapter's persisted-claim resume path unreachable.
5. The "framework-neutral" checkpoint layer is torch + SafeTensors only (`hf2l/checkpoint_utils.py:13-14, 19-21, 93, 162-183`); torch and huggingface_hub are unconditional dependencies (`pyproject.toml:11-16`) loaded by every CLI including `client_upload` and `--check-only`; example code is installed as a top-level `examples` package that the library imports (`pyproject.toml:59`; `hf2l/plugins/lenet_poc.py:16-17`).
6. `hf2l/exchange/api.py` (1,055 lines) is a god object: domain rules raise `HTTPException` through `fail()` (`:62-64`, 91 sites), the worker and CLI depend on the HTTP-layer `Service` (`hf2l/exchange/worker.py:23-190`; `hf2l/exchange/cli.py:35-37`), and record/blob/claim states are 100+ bare literals and the released-state set is spelled three times (two tuples at `api.py:37`, `worker.py:15` and an SQL literal at `hf2l/exchange/migrations.py:39`).
7. The test suite has no fakes or contract tests: the owner is driven only through patched `sys.argv` and a hand-rolled `Mock` (`tests/test_fedavg_readiness.py:28-39, 82`), HF/JFrog stores are built with `object.__new__` (`tests/test_poc.py:351-449`), exchange rules are reachable only through HTTP + RSA JWT + Moto (53 tests take ~44 of ~45 s), and fixtures are copied between modules by attribute loop (`tests/test_exchange_hardening.py:563-566`).

**Shape of the proposed design.** The owner has waived backward compatibility, so the design is a single cut rather than a repoint: one console script `hf2l`, manifest schema 3 with workflow-neutral `hf2l_*.json` names, a redefined `/v1` contract, a greenfield database (`create_all` plus a one-row `exchange_schema` table) and a rewritten test suite. Two stdlib halves share `hf2l/common` (fs and config helpers, the four version axes), plus a single `round` -> `exchange.profiles` edge for the FedAvg profile value: `hf2l/core` owns the typed FL documents, the FL-vocabulary-free `ArtifactStore` port with a three-member `Capability` set and optional Protocols (`SupportsAncestry`, `SupportsClaims`, `SupportsNamedRevisions`, `RepositoryAdmin`), and the `Hf2lError` tree; `hf2l/exchange/vocabulary.py` and `profiles.py` own every exchange literal and a JSON `WorkflowProfile` stored per space, so the service names no FL concept and a `profile=null` space is a plain artifact exchange. The FedAvg profile value lives on the FL side (`hf2l/round/exchange_profile.py`), is sent at space creation and is read back through `GET /me`. Above the port sit a torch-free checkpoint layer (`FormatSpec` sniff/discover, numpy and torch `ArrayOps` backends, one `average()`), an `Aggregator` seam (FedAvg, FedProx), `run_round` over pure stages with a typed `RoundResult` and exit codes, and `hf2l/round/channel.py` as the only module that spells FL names into store calls. `LocalStore` is the quickstart backend and the contract fake; HF, JFrog and the exchange adapter pass the same `StoreContractTests`. The exchange service is split into 18 modules (`runtime`/`Tx`, domain use-cases, HTTP edge, worker, SDK) that preserve the space-lock-first transaction, the attempt-owned blob lease with its CAS commit and the fenced-claim flow. About 57 modules for about 6,400 lines; layering is an allowlist enforced by `tests/test_layering.py`.

**Recommended order of work.**

1. **WP0 -- reset, goldens, behaviour inventory, layering gate.** Aggregate three fixtures with the current implementation and store hashes plus CPU metadata under `tests/goldens/`; extract `tests/support/scenarios.md` from the four test modules that will be deleted; move review and design markdown to `docs/history/`; commit `tests/test_layering.py` with the target allowlist scoped to the new package prefixes.
2. **WP1 -- the kernel.** Write `hf2l/common`, `hf2l/core` (documents, `ArtifactStore` port, errors), `hf2l/checkpoint` (torch-free discovery, `ArrayOps`, one `average()`) and the stdlib `hf2l/exchange/{vocabulary,profiles}.py`, deleting `hub_helpers.py`, `checkpoint_utils.py`, `data_utils.py`, `exchange/protocol.py` and the four legacy test modules (none of them runs without `hub_helpers`). This package freezes the port, the vocabulary and the profiles; everything after it can run as two tracks.
3. **WP2 -- stores** (`REGISTRY`, `LocalStore`, `HfApiStore`/`JFrogApi`, HF, JFrog, `StoreContractTests`, the live Hub/Artifactory smoke checklist), deleting `hf2l/backends/*` except the exchange adapter. With a second engineer, **WP4 -- the greenfield exchange service** starts in parallel.

## Method

The review was run as a structured, multi-reader exercise against commit `714fd66` (branch `main`; 21 commits in history).

- **Subsystem maps.** Ten independent readers each produced a map of one unit: FL core and client pipeline (CORE), owner FedAvg orchestration (OWNER), ModelStore backends (BACKENDS), exchange API layer (API), exchange persistence/worker/storage (PERSIST), exchange SDK and adapter (SDK), test suite (TESTS), documentation set (DOCS), module dependency graph and layering (DEPS), and cross-cutting conventions (XCUT). Each map recorded responsibilities, interfaces, dependencies and "extension walkthroughs today" (how many files change for a realistic extension).
- **Adversarial verification.** Every candidate finding was independently re-checked against HEAD by a verifier who confirmed or corrected each `file:line`, adjusted severity, and refuted claims that did not hold (for example, the claim that the relay is untested, the claim that a recover-after guard mixes host and database clocks, and several non-existent line numbers). Verifier-added findings are marked as such in the source notes. The result is 177 confirmed findings.
- **De-duplication and theming.** The 177 findings were grouped into 12 themes; 46 findings that restate another finding from a different reader's angle were folded into the first-listed ID (table below), leaving 131 rows in section 4. Every kept finding appears exactly once.
- **Design competition.** Three independent designs were written against the themes and scored by three judges on generality, maintainability, feasibility, preservation of strengths and evidence accuracy: Incremental Consolidation (115), Domain-Core-First (109), Protocol-First Exchange Platform (109). The judges also produced a list of concerns (wrong line numbers, inflated counts, premature entry points, schema bumps, sequencing of FL seams last, callable-vs-data profiles).
- **First synthesis and critique (superseded; see Alternatives).** The first synthesis revised the winning design to adopt the two-layer stdlib split from Domain-Core-First and the data-only profile from PFX, then went through a feasibility and coverage critique that removed items judged unimplementable under the compatibility constraint (jsonschema in a stdlib core, `rules.profile` inside a `dict[str, KindRule]`, a single-status error code while `claim_not_active` was raised with 409 and 412) or disproportionate under it (in-memory blob store, renewer thread, Ledger class, sectioned Settings). The constraint change below reinstated the single-status registry (feasible once the `/v1` error contract could change; Principles, item 5) and the four disproportionate items, now `MemoryBlobStore` in `tests/support`, `ledger.renewing`, `Ledger` and sectioned `Settings`.
- **Constraint change and second competition.** The owner then removed the backward-compatibility and migration constraint ("No need for migration. We don't guarantee backward-compatibility."), so the competition was re-run with three clean-slate designs scored by three judges: "FL-Core Clean Slate: `hf2l.fl` domain core, capability-scoped `hf2l.stores`, and a profile-as-data generic exchange" (132), "XP1 -- Exchange Platform First, clean slate: one protocol package, a layered generic exchange, a thin typed SDK, and a small FL layer over an FL-free store port" (125), and "One vocabulary, six seams: a minimal-concepts rewrite of hf2l (single `hf2l` CLI, stdlib FL kernel, LocalStore as the second real backend, exchange split into vocabulary/domain/http)" (140). The winner was synthesized with the FL-free port and profile-as-data of the other two, critiqued (layering allowlist versus sketches, an infeasible byte-identity gate, BF16, a blob-shaped `WorkClass`, profiles registered as server code) and revised into section 5; the measurements behind the numeric gate were re-run for this revision. The earlier compatibility-preserving design is summarized under Alternatives.

## Current architecture

### Component map

- `hf2l/` (CLI entry points, one `main()` each; all import `hf2l.backends`)
  - `init_repo.py` -- create repository, run plugin `initialize_model`, write round-0 `fedavg_round.json` (`:128-143`), publish.
  - `client_download.py`, `client_upload.py` -- option A: any trainer between two step functions.
  - `client_train.py` -- option B: wraps a plugin's `train_model` around the same two steps.
  - `client_steps.py` -- `download_client_round` / `upload_client_update`; the single submission-manifest writer (`:93-105`).
  - `owner_fedavg.py` -- the only coordinator: pin `main`, select (explicit / discover / claim), allowlist, ancestry, manifest validation, download, hash + schema check, aggregate, evaluate, round record, publish, claim cleanup (`:222-512`).
  - `create_allowlist.py`, `allowlist.py` -- casefolded author-to-participant map.
  - `checkpoint_utils.py` -- checkpoint contract (`config.json` + `model.safetensors` or index + shards), `CheckpointLayout`/`TensorSpec` discovery via header reads, `validate_compatible`, shard-streamed `aggregate_checkpoints`.
  - `hub_helpers.py` -- manifest filenames and `SCHEMA_VERSION` (`:12-16`), JSON/hash/path helpers.
  - `plugin_loader.py`, `plugins/` -- alias table (`:17-20`) or local `.py`; duck-typed `initialize_model` / `train_model` / `evaluate_model`; two example plugins over `examples/`.
  - `training.py`, `data_utils.py` -- fixed SGD/CrossEntropy loop and seeding used by the example plugins.
- `hf2l/backends/` -- `ModelStore` ABC (`base.py`), `HuggingFaceStore`, `JFrogStore`, `ExchangeStore`, `factory.py` (`--backend/--endpoint/--token` + env).
- `hf2l/exchange/` -- the service: `api.py` (Service + 29 routes), `schemas.py` (pydantic inputs + FedAvg profile constants), `models.py` (8 tables, engine, `database_time`), `migrations.py` (one v1->v2 step), `storage.py` (`S3BlobStore`), `auth.py` (RS256 `at+jwt`), `config.py` (flat `Settings`), `leases.py`, `worker.py` (recovery/verify/cleanup/retention), `cli.py`, `protocol.py` (shared wire constants), `client.py` (httpx SDK).
- `examples/` -- installed as a top-level package (`pyproject.toml:59`): LeNet/VGG models, MNIST/CIFAR adapters, `hf_webhook_relay.py` (WSGI).
- `.github/workflows/` -- `fed_avg.yml` (readiness job, then aggregate + publish pinned to the checked base), `exchange_tests.yml` (SQLite/Moto on 3.10 and 3.12; PostgreSQL 18 + MinIO on 3.12).
- `docs/` -- README tutorial, Marp slide deck + PDF, exchange design proposal, exchange operator guide, HF workflow guide, review findings and remediation logs (2,901 lines total).

### Dependency and layering picture

Four de-facto tiers (from the DEPS survey; static intra-package graph is acyclic):

1. stdlib-only leaves: `hub_helpers`, `backends/base`, `plugin_loader`, `data_utils`, `exchange/models`, `exchange/storage`, `exchange/auth`, `training` (torch), `examples/*`.
2. one third-party family each: `checkpoint_utils` (+torch/safetensors), `backends/{huggingface,jfrog}` (+huggingface_hub), `exchange/client` (+httpx), `exchange/{api,worker,schemas,leases,migrations}` (+fastapi/sqlalchemy/boto3/jwt/pydantic).
3. composition: `backends/factory`, `backends/exchange`, `client_steps`.
4. seven argparse CLIs.

Three structural inversions:

- The generic exchange imports FedAvg manifest names: `hf2l/exchange/protocol.py:5` imports `ROUND_FILE, SUBMISSION_FILE` from `hub_helpers`; `api.py:27` imports `INLINE_MANIFEST_NAMES` from it and enforces them as reserved attachment names (`api.py:210-221`).
- The library imports demo code: `hf2l/plugins/lenet_poc.py:16-17` imports `examples.lenet_model` and `examples.mnist_data`; `examples/mnist_data.py:12` imports `hf2l.data_utils` back.
- The workflow branches on backend names instead of capabilities: eight name-equality sites in all, six literal `== "huggingface"/"jfrog"/"exchange"` comparisons (`owner_fedavg.py:77, 231, 237, 241, 336, 500`) plus two checks of a persisted backend tag against `store.name` (`owner_fedavg.py:266`, `client_steps.py:73`). Every "eight name-equality sites" below refers to this set.

A different triple, "the three inverted `hub_helpers` imports" (`exchange/protocol.py:5`, `checkpoint_utils.py:16`, `backends/exchange.py:11`), names the three modules outside the FL CLI layer that import manifest names from `hub_helpers`; the design removes those edges in step 1 (XCUT-7, BACKENDS-3).

Measured imports in the venv: `import hf2l.backends` loads huggingface_hub even for `--backend exchange` (`backends/__init__.py:3-4` -> `factory.py:10-11`); `import hf2l.owner_fedavg` loads torch, safetensors, huggingface_hub and httpx; `import hf2l.exchange.client` loads only httpx plus `protocol`/`hub_helpers`. At runtime `api.py:792, 836` lazily import `worker.commit` while `worker.py` calls `service.sessions/storage/release/emit/blobs` on the `api.Service` object without a declared interface -- a mutual dependency invisible to static analysis.

### Runtime flows

**Client round trip (option A/B).** `client_download` -> `factory.make_store` -> `store.resolve_revision(repo, base)` -> `download_snapshot` into `work_dir/base_model` (`client_steps.py:32-40`) -> write `fedavg_client_context.json` (`:42-51`, includes `backend: store.name`). Trainer (any code, or `client_train` calling the plugin's `train_model(base_dir, output_dir, options)` with `options["participant"]` injected, `client_train.py:51, 59`) writes `work_dir/trained_model`. `client_upload` -> `upload_client_update` re-reads the context (`client_steps.py:66-90`, rejects a backend mismatch at `:72-76`), `discover_checkpoint` + `validate_compatible` (`:86-88`), hashes the artifacts, writes `fedavg_submission.json` (`client_steps.py:93-105`), and `store.publish_submission(...)` (`client_steps.py:108`) -- HF: `create_commit(create_pr=True)`; JFrog: unique named revision; exchange: `training.update` record with inline manifest.

**Owner FedAvg round.** `owner_fedavg.main` (`:222-512`): validate flags, `require_new_directory(output_dir)` (`:249`), `make_store` (`:250`), `resolve_reference(repo, "main")` (`:251`), read the base round record (`:260-270`), select candidates via `explicit_submissions` / `discover_submissions` / `claim_submissions` (`:272-283`), casefolded allowlist (`:287`), ancestry (`:303-304`), per-candidate manifest download and `validate_submission_manifest` inside `except (ValueError, OSError)` (`:314-343`), duplicate-participant check (`:344-348`), readiness JSON if `--check-only` (`:354-362`), full downloads and hash/schema checks (`:375-412`), coefficients (`:414-418`), `aggregate_checkpoints` (`:420-428`), optional plugin `evaluate_model` (`:430-439`), round record (`:441-463`), `publish_aggregate(expected_base=..., claim=...)` (`:479-501`), and `abandon_claim` in the `except` block (`:504-511`).

**Exchange upload / verify / publish.** SDK `put_record` (`client.py:147-213`): fingerprint the request, load or save a resume state file, `POST /records` (draft), `PATCH` metadata, then per attachment `POST .../uploads` (server reserves a key `spaces/{space}/blobs/{blob}` and part size, `api.py:684-687`), `POST /uploads/{id}/parts:authorize` for presigned PUT grants, upload parts on a token-less transfer client, `POST /uploads/{id}:complete` (`worker.commit` transition to `completing`/`verifying`), then `POST /records/{id}:publish` and poll until the worker verifies size and SHA-256 by streaming the object (`storage.py:108-117`) and the record reaches `ready`.

**Claim-fenced publication (exchange only).** Owner resolves `main` (adapter caches it in `main_refs`, `backends/exchange.py:86-87`), `claim_submissions` -> `POST /claims` (`api.py:935-976`): server freezes the newest ready `training.update` per participant for the pinned base (`frozen_inputs`, `:389-417`), enforces the minimum (`:428-430`), returns id + fence; adapter persists `exchange-claim.json` (`:239-296`). After aggregation `publish_aggregate` uploads a `model.global` record with `input_record_ids` scraped from the on-disk round record (`:326-328`) and calls `POST /claims/{id}:publish` (`:330-331`), which checks the provenance subset and moves `main` under `If-Match` (`api.py:1043-1050`). Any failure abandons the claim (`owner_fedavg.py:509`).

### What works well

- Checkpoint discovery reads SafeTensors headers without materialising weights, and aggregation streams shard by shard under `ExitStack` with NaN/inf rejection, non-floating equality and float64 promotion (`checkpoint_utils.py:58-121, 162-183, 208-251`). This is the right core; it needs a seam, not a rewrite.
- Immutable-identity discipline: resolve a ref, download by immutable id, `expected_base` precondition on publish, post-publish verification (`huggingface.py:174-175`, `backends/exchange.py:314, 335`).
- One submission-manifest writer shared by option A and option B clients (`client_steps.py:93-105`), so both integration paths produce identical protocol documents.
- The exchange's distributed-systems core is careful: space-row-lock-first transaction ordering (`api.py:235-250`), database clock for lease decisions (`models.py:18-22`), fenced claims, `If-Match` CAS on refs, idempotency digests with replay (`api.py:288-318`), `worker.commit` as a CAS transition on token + state (`worker.py:73-77`), bounded pydantic inputs (`schemas.py:27-28`), versioned-bucket immutability, and a separate transfer client that never carries the bearer token (`client.py:50-52`).

- DI seams already exist at the composition roots: `create_app(settings, storage)`, `Service(settings, storage=)`, `S3BlobStore(settings, client=)`, `ExchangeClient(http=, transfer=)`, `ExchangeStore(client=, wait_seconds=)`. The design extends these rather than inventing a second style.

### Theme 1 -- FedAvg is the only workflow and it is hard-wired at every layer: no Aggregator / Workflow / Profile seam

**Statement.** The one algorithm is encoded as control flow and constants. Weighting is an inline `if/else` and the reduce a fixed convex combination; the algorithm is a free-text string; the `>=2` quorum is a literal duplicated in owner, server schema and CI; the manifest validator rejects any base other than current `main`. In the exchange, `workflow` is a free label used only in a uniqueness key while every handler dereferences `MAIN_REF`/`UPDATE_KIND`/`PROVENANCE_FIELD` and `check_profile` forces the FedAvg kinds on every space. FedProx, Scaffold/FedOpt, secure aggregation, async FL and any non-FL tenant each require forking `owner_fedavg.main` and editing six or more `api.py` functions. **Severity: high.**

**Design requirement.** An `Aggregator` interface (select, weights, reduce with server state) selected by `--algorithm`, with `algorithm: {name, version, params}` recorded in round and submission manifests and propagated to trainers; a `WorkflowProfile` value (kinds, result kind, target ref, provenance field, reserved names, selection/acceptance policy, minimum, lease policy) registered with the exchange and consulted by claim/ref/record handlers; a `ClaimRequest` carrying workflow/minimum from owner to server so the quorum has one owner per trust domain; the target ref an explicit parameter defaulted only at the CLI.

### Theme 2 -- Layering inversion and no single protocol vocabulary

### Theme 9 -- Exchange infrastructure and domain primitives lack seams

**Statement.** Each cross-cutting primitive exists once as an ad-hoc implementation. Storage: `S3BlobStore` is concrete; botocore exceptions and S3 error codes are caught in `api.py` and `worker.py`; raw boto part dicts are read by a handler; the key layout is chosen by the API; bare `ValueError` carries four meanings. Identity: one RS256/`at+jwt`/single-issuer authenticator built inside `Service`, with principal derivation duplicated in the SDK. State: 100+ string literals, transitions guarded inline, claim liveness recomputed six ways. Leases: two blob-lease acquisitions and a third inline claim pattern with one heartbeat thread per blob. The quota ledger is mutated in four places; timestamps come from three clocks; migrations are one unversioned step; `Space.rules` is an untyped blob; event kinds are free strings; the worker is a bag of functions with string outcomes; domain rows have no lifecycle end. **Severity: high.**

**Design requirement.** A `BlobStore` Protocol with provider-neutral vocabulary and a `StorageError(permanent, code)` hierarchy translated inside adapters; an injectable `IdentityProvider` with `principal_id` defined once and `Member.issuer` stored; `states.py` enums with a declarative transition table and one `transition()`; one lease helper for blobs and claims; a quota `Ledger` with `reconcile()`; a `Clock` protocol memoised per transaction and no host-clock defaults; a `DatabaseAdapter` as the only dialect owner; versioned ordered migrations with a CI metadata diff; typed `KindRule`; an `EventKind` enum; a `WorkClass`/`Outcome` protocol with metrics; terminal-row retention defined in the state table.

### Theme 10 -- Cross-cutting conventions are inconsistent across layers

**Statement.** Configuration: a validated flat `Settings` on the server whose auth/storage validation runs for worker-only and `init-db` processes, versus three client-side resolution sites with two boolean grammars for one variable name and no typed config; a test hostname in the production TLS policy. ### Theme 11 -- Test architecture has no fakes or contract tests

**Statement.** Testability follows the seams and the seams are missing. ## Proposed design

### Thesis

The owner has waived backward compatibility ("No need for migration. We don't guarantee backward-compatibility."), so this is a one-cut rewrite, not a repoint: package and module names, console scripts and flags, the manifest schema, the `/v1` bodies, the SDK, the database and the test suite are all replaced. The shape is the one the second competition scored highest, "One vocabulary, six seams" (140), with the FL-free store port and the profile-as-data of the two other clean-slate designs folded in:

1. A stdlib FL kernel (`hf2l/common`, `hf2l/core`) owns every FL literal, the typed documents (`hf2l_*.json`, schema 3), the FL-vocabulary-free `ArtifactStore` port with a three-member `Capability` set and optional Protocols, and the `Hf2lError` tree.
2. A torch-free checkpoint layer whose pluggable parts are a `FormatSpec` (sniff/discover) and `ArrayOps` backends (numpy by default, torch for BF16), with `average()` kept as the one home of the NaN/inf, non-floating-equality and float64-promotion rules that live in `checkpoint_utils.py:162-183` today.
3. One `ArtifactStore` port proven by a real `LocalStore` (quickstart backend and contract fake); HF, JFrog and the exchange adapter pass the same `StoreContractTests`; `hf2l/round/channel.py` is the only module that maps FL vocabulary onto store calls.
4. One `Aggregator` seam (FedAvg, FedProx) and `run_round` over pure stages with a typed `RoundResult`, behind a single `hf2l` console script.
5. A generic exchange whose coordination behaviour is a JSON `WorkflowProfile` stored per space and echoed by `GET /me`; `hf2l.exchange` imports nothing from the FL side, and the FedAvg profile value lives in `hf2l/round/exchange_profile.py`.

The revision closes every critique the judges recorded. The layering allowlist now matches the sketches (`RoundConfig` lives in `round/config.py`, the SDK takes plain kwargs and a `state_dir`, `stores.exchange` may import `exchange.{sdk,vocabulary,profiles}`, plugins are listed). The exchange adapter has a stated kind-selection rule, and the manifest-versus-binding check at `backends/exchange.py:112-114` moves to `stages.filter_eligible` over `Candidate.participant`/`Candidate.base`. JFrog derives revisions from the AQL item path (the layout `tests/test_poc.py:432-459` already assumes) and mints them through `SupportsNamedRevisions`. Upload use-cases take the `Runtime` so the CAS commit stays in its own transaction (the `worker.py:70-93` shape); the server keeps a ~25-line `ledger.renewing` context manager with the `leases.py:34-59` semantics. `AdvanceRef.expected` may be `None` (create). `Heartbeat` is injectable. `WorkflowProfile.validate` ports `check_profile` (`api.py:160-190`) verbatim. The numeric gate is operand-scaled with CPU-tagged goldens and no wall-time assertion, stated in the form that was measured in the venv (see Principles, item 11). The exchange tree is folded to 18 modules and the package lands at about 57 modules for about 6,400 lines, replacing 36 modules and 5,416 lines.

### Principles

1. **One owner per literal, and the owner is a stdlib module.** FL names, schema version, document types, the store port, errors and policy values live in `hf2l/core`; exchange codes, statuses, states, roles, actions, event kinds, routes, limits and the `ExchangeFailure` classes live in `hf2l/exchange/vocabulary.py`; `WorkflowProfile`/`KindSpec` live in `hf2l/exchange/profiles.py` with no FL names and no built-in value; the four version axes (manifest 3, plugin API 1, HTTP `v1`, DB revision 1) live in `hf2l/common/versions.py`, importable by both halves. The FedAvg profile value (kinds `training.update`/`model.global`, target ref `main`, provenance field `input_record_ids`, document names from `FILES`, minimum 2, today spread over `schemas.py:13-18`, `api.py:39, 49-50` and `backends/exchange.py:191-213, 335`) is owned by `hf2l/round/exchange_profile.py`, sent at space creation and read back via `GET /me`.
2. **Layering is an allowlist over `git ls-files`, enforced by `tests/test_layering.py`, and the sketches obey it.** `common` imports nothing from `hf2l`; `core` <- `common`; `checkpoint` <- `common`, `core.errors` (never `core.protocol`); `stores.{local,hfapi,huggingface,jfrog}` <- `common`, `core`; `stores.exchange` <- `common`, `core`, `exchange.{sdk,vocabulary,profiles}`; `round` <- `common`, `core`, `checkpoint`, plus `exchange.profiles` from `round/exchange_profile.py` only (the sole `round` -> `exchange` edge); `plugins.api` <- `common`, `core`; `plugins.{lenet,vgg_cifar10}` <- `plugins.api`, `examples`; `examples` imports no `hf2l` module; `cli` is the composition root and may import everything (service modules lazily); `exchange.{vocabulary,profiles}` <- `common`; `exchange.sdk` <- `common`, `exchange.vocabulary` (third-party: httpx only); every other exchange module <- `common`, `exchange.*`; no exchange module imports `core`, `checkpoint`, `round`, `stores` or `plugins`. Package `__init__` files (except the lazy `stores.REGISTRY` dict) contain no `hf2l` imports, asserted by the same test. Between WP0 and WP6 the test is scoped to the new package prefixes: a cutover-window accommodation, not a shim, because the legacy modules are dead code awaiting deletion rather than exempted behaviour; WP6 removes the scoping once no legacy module remains.
3. **Behaviour is selected by capability, by `isinstance` against a `runtime_checkable` Protocol, or by a value, never by a name string.** `Capability = {IMMUTABLE_TAGS, BINDS_PARTICIPANT, PREFILTERS_BY_BASE}`, each with a named consumer (tag warning; resolver choice and binding check; prefilter skip). Atomic publish is a contract requirement proven by `StoreContractTests`, not a flag; generation display uses `ResolvedRef.generation is not None`. Optional behaviour: `SupportsAncestry`, `SupportsClaims`, `SupportsNamedRevisions`, `RepositoryAdmin`. Every `store.name ==` / `args.backend !=` branch is deleted, nine sites in all: the eight name-equality sites of section 3 (`owner_fedavg.py:77, 231, 237, 241, 266, 336, 500`; `client_steps.py:73`) plus `owner_fedavg.py:55`, which section 3's count omits because it compares the submission manifest's persisted `backend` tag with the expected backend rather than with `store.name` (`:55` and `:266` are the two persisted-tag checks on the owner side, the submission manifest's and main's round record's); the persisted `store` label is informational; the HF "close PRs after review" note (`owner_fedavg.py:500-501`) becomes `PublishResult.warnings`.
4. **Policy travels as values above the store.** `SelectionPolicy`, `Eligibility`, `ClaimRequest`, `AlgorithmSpec`, `CompatibilityPolicy`, `RunState` and the pinned `ResolvedRef` are explicit parameters; stores hold no per-call instance state (`backends/exchange.py:80-82, 209-211, 260-263` today). `hf2l/round/channel.py` is the only module that maps FL vocabulary (`FILES` names, participant, round, base, claim) onto store calls, labels, documents and named revisions; it is a module of functions, not role-view classes (recorded decision: eight-method port, one consumer).
5. **Typed errors decide control flow; exit codes and HTTP statuses are edge concerns.** Client code raises `Hf2lError` subclasses; the owner skips a candidate only on `InvalidSubmission`, retries `StoreError(transient)`, and never catches bare `ValueError` from a store (`owner_fedavg.py:339` today). Exchange domain code raises `ExchangeFailure` subclasses whose class fixes the status and whose code must be in `ERRORS` with that status (asserted at construction). Every code has exactly one status: renew returns `412 claim_fence_changed`, `412 claim_lease_expired` or `409 claim_completed` instead of `412 claim_not_active` (`api.py:1006`); acquire-replay and GET keep `409 claim_not_active` (`:975, :998`). `ErrorCode` carries `category` and `stale_claim` so the adapter never keeps its own code tuple (`backends/exchange.py:16`).
6. **Two implementations only when the second is useful in production or the quickstart, or removes a slow oracle without adding production surface.** `LocalStore` beside HF/JFrog/exchange (quickstart backend and contract fake); numpy beside torch `ArrayOps` (torch-free coordinator for F16/F32/F64/int; BF16 needs the torch extra and `get_ops` says so, since `safetensors.numpy` raises `TypeError: data type 'bfloat16' not understood`, verified with safetensors 0.8.0); `profile=null` beside `FEDAVG`; FedProx beside FedAvg. `MemoryBlobStore`, `StaticIdentityProvider`, `FakeClock` and `FaultTransport` live in `tests/support` and are injected through `build_runtime(storage=, identity=, clock=)` and `ExchangeClient(http=, transfer=)`; no loopback dev route, no shared-token auth, no `AuthSettings.provider` knob until a second provider exists.
7. **One module per responsibility, not per class.** Registries are plain dicts in one module each (`stores/__init__.py` `REGISTRY`, `round/aggregator.py` `AGGREGATORS`, `checkpoint/format.py` `FORMATS`, `plugins/api.py` `PLUGINS`, `exchange/storage.py` `STORAGE_PROVIDERS`); argparse choices, env tables and OpenAPI enums derive from them. No entry-point discovery. Target: about 57 modules for about 6,400 lines; a new file needs a one-line responsibility that no existing module already owns.
8. **Preserve the verified strengths as behaviour.** Header-only layout discovery with the precise key/shape/dtype diff (now also verifying header length and data offsets against file size); the `ExitStack` shard-streaming reduce (`checkpoint_utils.py:208-251`) with NaN/inf rejection, non-floating equality and float64 promotion kept in one function over `ArrayOps` primitives; immutable-id discipline (resolve, download by id, expected-base precondition, verify after publish); one submission-manifest writer for options A and B (`client_steps.py:93-105` today); two-phase check-only readiness via `result.json`; the fenced claim released exactly once in `finally`; `If-Match` CAS; the quota ledger; provenance `input_record_ids` passed on `AdvanceRef`; digest-verified transfers over a token-less transfer client; space-lock-first transaction ordering (`api.py:235-250`, preserved in `runtime.transaction`); attempt-owned blob leases with the CAS commit decided on the database clock in its own transaction and shared by API and worker (`worker.py:70-93`); server-side lease renewal during long steps (`leases.py:34-59`); SQLite `BEGIN IMMEDIATE` + `foreign_keys=ON`; bounded pydantic inputs; versioned-bucket immutability; the existing DI seams.
9. **Library code logs and returns diagnostics as data.** `logging.getLogger(__name__)` everywhere; `RoundResult.skipped`, `PublishResult.warnings`, `Discovery.skipped` replace printed skips (`backends/exchange.py:264-268`, `owner_fedavg.py:341`); `hf2l/cli` installs handlers and owns the `key=value` and `--json` renderings. A grep test asserts no `print()` outside `hf2l/cli` and `hf2l/examples`.
10. **Documents are opaque to stores.** The channel writes `hf2l_*.json` into the publish folder, lists them in `paths` and names which are `documents` (`DocumentSpec` with an optional `bounded(budget)` callback and overflow name); the exchange store inlines them under `metadata["documents"]`, records any overflow attachment under `metadata["documents_complete"]`, and never re-reads provenance from disk (`backends/exchange.py:326` today). Published server state lives under `server_state/` (hashed separately, excluded from checkpoint hashes and from non-checkpoint copying); local run state lives under `<state_dir>/.hf2l/` and is never published (today the adapter writes `exchange-claim.json` and `*.exchange-upload.json` beside the folder, `backends/exchange.py:14, 167-169`).
11. **Acceptance gates are feasible and derived, and were measured before being written down.** Torch `ArrayOps` must be bit-identical to the WP0 goldens on a runner whose recorded CPU capability matches, otherwise within the operand-scaled tolerance below. numpy `ArrayOps` must satisfy, per tensor with accumulator dtype `d`, `|numpy - torch| <= 2*eps(d)*sum|c_i|*max_i max|x_i|` on the accumulator values before the cast back to the tensor dtype, and both backends must be within the same bound of a float64 reference. Measured in the venv (torch 2.14.0, numpy 2.5.2, AVX2) over five coefficient sets, three magnitudes (0.01, 1, 100) and F16/F32/F64 inputs on 512x1024 tensors: worst ratio 0.34 of the bound, never above it. A "one output ulp" criterion on cast float16 outputs is *not* feasible: under cancellation (three inputs of magnitude 100 with coefficients 1/3) the two accumulators differ by 5e-6, which is 82 float16 ulps at a near-zero output, so cast outputs are gated by `max(one output ulp, the accumulator bound)`. Goldens use three examples-weighted clients with coefficients (0.2, 0.3, 0.5) because (0.5, 0.5) is bit-identical across backends and would not exercise the gate. No wall-time assertion in CI: the streaming property is asserted with a recording `ArrayOps` (at most `clients + 1` shards open at once, each opened once) and the 500 MB benchmark is a manual script. Registry tests derive and print counts instead of asserting literals.
12. **Proportionality.** `requires-python >= 3.11` (native `StrEnum`; the owner is asked to confirm dropping 3.10, which `exchange_tests.yml:16` runs today; a 10-line polyfill in `hf2l/common` restores it); four generated artefacts (`openapi.json`, `errors.json` including the version axes, `env.md`, `documents.v3.json` emitted from the dataclasses); greenfield `create_all` plus a one-row `exchange_schema` table whose revision is bumped by hand with the first post-cutover change; no Alembic, metrics, admin UI, webhooks, entry points, event-driven loop trigger or re-rendered idempotency replay.

### Service layering and protocol-as-source-of-truth

`exchange/http/routes.py` parses input, opens `runtime.transaction(rt, space_id, actor, action=...)`, calls one use-case in `exchange/domain/*` and renders a pydantic view from `http/schemas.py`. Domain functions operate on a `Tx` (session, locked space, member, actor, `now`, storage, profile, kinds, ledger) and raise `ExchangeFailure` subclasses; the single handler in `http/app.py` maps them to status, `Retry-After` and `WWW-Authenticate` from `ERRORS`. The two documented exceptions are `domain/uploads.py`'s `start_upload`/`complete_upload`, which take the `Runtime` because the lease-take, the storage call under `ledger.renewing` and the CAS `commit()` must be three transactions, exactly as `api.py:790-859` and `worker.py:70-93` do today. The worker calls the same domain functions through the `Runtime` and `domain/uploads.commit`; it never imports `http`. `hf2l exchange serve` runs `uvicorn.run("hf2l.exchange.http.app:from_env", factory=True)`.

`exchange/vocabulary.py` and `exchange/profiles.py` are the source of truth: `http/schemas.py` builds its `Literal`s and enums from them, domain code raises their codes, `sdk.py` imports states, `Routes` and `ERRORS`, the adapter reads the profile it needs from `GET /me` rather than importing anything, and `hf2l export-contract` writes `docs/generated/{openapi.json, errors.json, env.md}` from `build_runtime(Settings.from_env("export"))` without database, S3 or JWT configuration. The FL side contributes exactly one value across the boundary, `FEDAVG` in `round/exchange_profile.py`, and it travels as JSON.

### Risks and costs

- **No green oracle across the cut for the exchange.** Regressions in space-lock ordering, `once()` replay, the blob CAS commit, the quota invariant and the remediated findings are caught only by the new suite. Mitigation: `scenarios.md`, extracted and reviewed in WP0 while the four legacy test modules still run (WP1 deletes `hub_helpers.py`, which all four need at import or through `protocol.py:5`), with its "covered by" column checked at WP7; the WP0 goldens; mandatory S3-conformance and PostgreSQL-concurrency lanes.
- **HF and JFrog cannot be integration-tested here**; `FakeHfApi` is the only automated oracle. Unverified points: the JFrog HuggingFaceML item-path layout `models/<org>/<model>/<revision>/...` (assumed by `tests/test_poc.py:432-459`) and the `JFrogApi.create_commit` repair under the jfrog extra's `huggingface_hub<=1.18.0` pin (`pyproject.toml:40-42`; the dev venv has 1.30.0, where the bug does not surface). Both are on the WP2 smoke checklist, budgeted at one day and recorded in `OPERATIONS.md`.
- **Everything published or deployed by the current code becomes unreadable**: schema 3 and renamed filenames orphan existing repositories; the redefined `/v1` contract and the greenfield database mean existing deployments are recreated; the single `hf2l` CLI breaks operator scripts and `fed_avg.yml` (`--discover-prs` at `:63`, `readiness.json` at `:73`). The owner waived compatibility; README, CHANGELOG and `fed_avg.yml` say so in the same release, and `hf2l init --model-dir` re-seeds from an existing checkpoint.
- **The numpy backend is a second numerical implementation.** The operand-scaled gate holds with headroom in the venv (worst ratio 0.34 of the bound), but it is a tolerance, not identity; torch bit-identity to goldens is asserted only when the recorded CPU capability matches; float16 outputs under cancellation legitimately differ by many output ulps and are gated by `max(one ulp, bound)`. BF16 models still force the torch extra on the coordinator.
- **Profile-as-data with closed `InputSelection`/`ResultAcceptance` enums is a real ceiling**: asynchronous FL and multi-phase secure aggregation still require `domain/refs.py` code, a new enum member and a constraint change; README must not promise otherwise.
- **Envelope kind schemas validate only stable required keys server-side**; a malformed value inside an unlisted field passes the exchange and is caught by the owner's dataclass parse. Deliberate (a manifest field change must never strand a space) and recorded in `CONTRACTS.md`; `documents.v3.json` is the full client-facing contract.
- **No shipped local storage/identity providers**: `hf2l exchange serve` needs an S3-compatible endpoint and an RS256 token even for a laptop demo (one `docker run minio` plus `hf2l exchange dev-token`). `LocalStore` is the zero-infrastructure quickstart.
- **The `Runtime`-taking upload use-cases are a documented exception** to "the router opens the transaction"; a contributor who reshapes them into one transaction would silently hold the space lock across storage I/O. `test_uploads.py` asserts the lease-take and the commit happen in separate transactions (the expired-attempt scenario fails otherwise).
- **Dropping Python 3.10** (for `enum.StrEnum`) is an environment change the owner should confirm; a ~10-line polyfill in `hf2l/common` restores it.
- **Idempotency keeps storing the rendered view**; a view shape change replays the old shape within the retention window. Accepted and recorded; re-rendering is a later additive change.
- **`Heartbeat` and `ledger.renewing` share pooled clients/sessions with the work they protect**; a wedged pool stalls both. Per-call timeouts shorter than the renewal interval, pool size >= 2 and tests with blocked transfers prove renewals continue; `ClaimLost` is a distinct exit code so a coordinator restarts rather than publishes.
- **`LocalStore` is single-host** (`O_EXCL` lock, file ancestry); it is a quickstart/test backend, not a multi-host coordination store, and the docs say so.
- **Generated artefacts create merge friction**: route, code, setting or manifest changes require rerunning `hf2l export-contract`. Intended; kept to four.
- **The fast lane relies on `starlette.testclient.TestClient` being an `httpx.Client`** (verified with starlette 1.6.0) for `ExchangeClient(http=TestClient)` and the `MockTransport` bridge; the service extra pins `starlette<2` and the harness has a fallback (uvicorn in a thread on 127.0.0.1) if that changes.
- **Schedule concentration in WP4** (14 days, security-sensitive, least reusable code). Slip there delays WP5 and the exchange path of pillar 3; the parallel plan depends on WP1 freezing the port, vocabulary and profiles.

### Explicitly not doing

## Alternatives considered

**FL-Core Clean Slate (132 points).** A stdlib `hf2l.fl` domain core (typed manifests at schema 3, `CheckpointLayout` with a pluggable `CheckpointCodec`, `Aggregator` with FedAvg and FedProx, selection/eligibility/participant policies, an FL-free `ArtifactStore` with `list_detached(document=)`), capability-scoped `hf2l.stores` adapters including a zero-dependency `LocalStore`, and a generic exchange whose only FL knowledge is a JSON `WorkflowProfile` stored per space and read back via `/me`. Its FL-free port and profile-as-data were the strictest answers to themes 2 and 3 and are adopted here. It was not chosen because its volume is the highest for a proof of concept (about 75 modules; `hf2l/fl` alone 18 modules for ~1,400 lines; four channel role-view classes, three resolvers, two identity providers; 10-13 engineer-weeks), because it mounted `/v1/_memory/{token}` loopback routes on the production FastAPI app to serve `MemoryBlobStore` grants (an unauthenticated write path by its own admission) and made `StaticTokenIdentityProvider` selectable in production settings, because it defined the profile twice (a stdlib dataclass and a pydantic `ProfileInput`) without an equality test and embedded the full manifest JSON Schemas in per-space kind schemas so a manifest field change strands existing spaces, and because its layout said `hf2l/fl` "imports common only" while `fl/exchange_profile.py` imports the exchange profile module, an edge its allowlist did not encode.

**XP1, Exchange Platform First (125 points).** One stdlib `hf2l.exchange.protocol` package as the single owner of every code, state, role, route, limit and profile enum; a layered generic exchange (HTTP -> use-cases -> domain state machines -> storage/identity/clock drivers); a thin typed SDK; and a small FL layer over an FL-free store port. Its "protocol is the single owner" discipline and typed `Detached | AdvanceRef` union are adopted. It was not chosen because it fragments into about 95 modules (nine tiny protocol files; `TypedDict` views duplicated by pydantic views and "asserted equal"; two `profile.py` and two `views.py` modules), because `CheckpointFormat.average()` pushes the NaN/inf, non-floating and float64 rules into every format implementation and so gives up the verified single-function strength (`checkpoint_utils.py:162-183`), because it puts exit codes on `RoundError` subclasses inside the FL library against its own "edge concern" principle, because five generated artefacts plus a `--help` snapshot and a `WorkClass`/`WorkerDriver`/`LeaseRenewer`/`Leasable` set exceed the brief's proportionality, and because its "exchange first" ordering schedules the FL layer at WP7 of 9 so no README pillar is demonstrable until roughly week 8 for one engineer.

**The previously chosen compatibility-preserving design (superseded).** Sections 5-8 of the earlier revision of this document kept every package, console script, CLI flag, the schema-2 manifests, the `/v1` bodies and the documented SDK signatures, used the five existing suites as the acceptance oracle after every commit, and paid for that with nine string-patched names kept as shims, one-release SDK deprecations, a status *set* on `ErrorCode` because `claim_not_active` is raised with 409 and 412, additive nullable columns plus a `schema_version` table, `Space.profile` as a nullable string selecting server-registered profiles, a `LegacyToPortAdapter` and a `LegacyModuleAdapter`, and 14 ordered steps over 6-8 weeks. When the owner dropped the constraint, all of that machinery lost its reason to exist. What survives from it, because the second competition's winner and judges independently confirmed it: the three-way stdlib split (`common` beneath `core` and the exchange vocabulary) with a layering allowlist enforced by a test; the FL-free `ArtifactStore` port with capabilities and optional Protocols; the profile as data (now a JSON value on the space rather than a server-registered name); `run_round` over eight pure stages with typed failures and exit codes; `average()` as the one home of the three numeric rules over array primitives; the `Tx`/`transaction()` preservation of `api.py:235-250`; the idea of contract suites and a support package under `tests/`; and the four generated artefacts. What it deliberately excluded and this design now includes, because compatibility no longer constrains them: `LocalStore` as a real second store, `MemoryBlobStore`/`FakeClock`/`StaticIdentityProvider` as injected test doubles, server-side lease renewal, `Ledger`, sectioned `Settings`, `Page[T]`, `Event.actor_kind/actor_id`, `Blob.provider/locator`, the single-status error registry, schema 3 and the single `hf2l` CLI.

Judge concerns that applied to all three clean-slate designs and are reflected above: every design deletes the hardening suite and re-derives fenced claims, `once()` replay, the blob CAS commit, quota invariants and space-lock ordering from scratch, so `scenarios.md` and the real-transport lanes are mandatory; HF and JFrog can only be tested against fake `HfApi`/request objects here, so a live Hub/Artifactory smoke checklist is a release gate; the "torch-free coordinator" claim holds only for non-BF16 models (`safetensors.numpy` rejects bfloat16); profile-as-data has a closed-enum ceiling that README must not paper over; all three drop Python 3.10; and every effort estimate for a full rewrite that also rewrites ~2,400 test lines and ~1,500 doc lines should carry slack on the exchange package. Two evidence corrections made while writing this section: the JFrog AQL literal is at `jfrog.py:198`, and the numeric gate as first proposed (ratio <= 0.25; one float16 output ulp) did not survive measurement, so it is stated above in the form that did.
